# LESNOY · Ежемесячный маркетинговый отчёт

## Контекст проекта

Веб-приложение ежемесячного маркетингового отчёта для ресторанной группы LESNOY (FIBONACCI FAMILY), два города: Ташкент и Бишкек. Хостинг — GitHub Pages (статика), база — Supabase (PostgreSQL + Auth). Язык интерфейса — русский.

Отчёт смотрит вся команда по публичной ссылке, заполняют 1–2 редактора раз в месяц.

## Файлы в репозитории

- `maket.html` — **утверждённый статичный макет (источник истины по дизайну и структуре)**. Финальное приложение должно выглядеть ровно так. Все данные июня 2026 зашиты в нём — использовать как сид.
- `index.html` — прошлая итерация с Supabase-логикой (auth по email/паролю, чтение/запись таблицы `reports`, JSONB-помесячно). Логику можно переиспользовать, но UI и структура данных там устаревшие — пересобрать под макет.
- `data.js` — устаревший сид июня (структура старая: есть `chats`, нет PR). Актуальные данные брать из `maket.html`.

## Структура страницы

Три таба: **Сводка / Ташкент / Бишкек**.

Порядок блоков в табе города (строго одинаковый в обоих):
1. **СММ — Instagram** — подписчики, прирост (подписки/отписки), просмотры (% от рекламы), охваченные аккаунты (+динамика), доля просмотров подписчиков, доля историй
2. **PR · Блогеры** — таблица: хэштег блогера / охваты / сумма чека, строка «Итого»
3. **Таргетированная реклама · Instagram** — карточки итогов (бюджет, охват, показы, клики, подписки, визиты профиля) + таблица кампаний
4. **Доставка · Яндекс Еда CPA** — только Ташкент (блок опциональный per-город)
5. **Отзывы гостей** — всегда в самом низу

Сводка: ключевые карточки (порядок: СММ → таргет → доставка → отзывы), таблица «Города рядом», «Выводы месяца» (карточки с тегом города и тоном: успех/внимание/нейтрально).

Терминология: «СММ — Instagram», «Таргетированная реклама · Instagram» (не Meta), «Доля рекламных расходов (ДРР)». Instagram всегда латиницей. Пояснения к метрикам (охват/показы/клики/визиты профиля, конверсии в доставке) — как в макете, не удалять.

## Автоматические расчёты (руками не вводятся)

- Цена подписчика = бюджет ÷ подписки (в каждой кампании, в итогах, в сводке)
- Цена заказа в доставке = затраты ÷ заказы
- Прирост Instagram = подписки − отписки
- Проценты позитива/негатива в отзывах = от общего числа
- Итоги PR-таблицы (сумма охватов и чеков)
- Вся вкладка «Сводка» считается из данных городов (кроме «Выводов месяца» — они пишутся руками)
- Итоговая строка таблицы кампаний НЕ равна сумме строк по охвату (пересечения аудиторий) — итоги вводятся редактором отдельно, из кабинета

## База данных (Supabase)

Хранение помесячно, JSONB:

```sql
create table reports (
  month text primary key,          -- '2026-06'
  data jsonb not null,
  updated_at timestamptz default now()
);
```

Только текущий год (2026), максимум 12 месяцев. Новый месяц создаётся копированием структуры последнего (названия кампаний сохраняются, цифры пустые).

Схема данных месяца (обновить относительно старого data.js):
- убрать все поля `chats` (переписки)
- добавить `visits` в meta и campaigns обоих городов
- добавить `pr: [{ hashtag, reach, amount }]` в каждый город
- `delivery` опционален per-город (сейчас только Ташкент)
- `findings: [{ city: 'tas'|'bis'|'', tone: 'win'|'warn'|'', text }]` на уровне месяца

## Авторизация и роли (главная задача)

Auth Supabase по email. Три роли:

1. **Просмотр** — по умолчанию, в т.ч. без входа. Только чтение.
2. **Редактор** — редактирование данных, создание/удаление месяцев.
3. **Суперюзер** — то же + назначение редакторов.

Реализация: таблица `user_roles (user_id uuid pk references auth.users, role text)` + RLS: запись в `reports` только для ролей editor/superuser; запись в `user_roles` только для superuser. Первого суперюзера назначить вручную в базе. Суперюзеру нужен простой UI управления ролями (список пользователей, выпадашка роли).

RLS-политики писать через security definer функцию проверки роли, чтобы избежать рекурсии политик на `user_roles`.

## Функции тулбара

- Селектор месяца (только существующие месяцы 2026)
- «✎ Редактировать» → инлайн-инпуты на месте значений, «Сохранить в базу» / «Отмена» (редактор+)
- «+ Месяц» (редактор+), «Удалить месяц» с подтверждением (редактор+)
- «⬇ Резервная копия» — выгрузка всех месяцев одним JSON/JS файлом (всем)
- «Войти» / «Выйти», статусная строка с ролью
- Если Supabase-ключи не вставлены — демо-режим из сида с плашкой

## Открытые вопросы (уточнить у владельца, не решать самостоятельно)

1. PR «сумма чека»: только бартер (счёт гостя-блогера) или также денежные размещения → возможно, нужна колонка «формат» (бартер/оплата)

## Технические требования

- Vanilla JS, один index.html + при необходимости config.js. Без сборщиков и фреймворков.
- supabase-js v2 с CDN.
- Ключи (Project URL, anon key) — в блоке CONFIG в начале файла с заглушками; service_role не использовать.
- Mobile-friendly (таблицы со скроллом, как в макете).
- Комментарии в коде на русском.
